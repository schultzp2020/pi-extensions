Product specification

Pi Model Advisor

Package @schultzp2020/pi-model-advisor under packages/pi-model-advisor. The extension advises which Pi-eligible model and thinking level should handle a proposed subtask while leaving orchestration to the caller.

Problem Statement

Pi users may delegate work through Paseo, a pure-Pi subagent extension, or another Pi-connected orchestrator. Existing routers commonly switch the parent session model, run on every prompt, or launch agents themselves. Those behaviors overlap orchestration and cannot be reused safely by callers that only need a model recommendation.

The recommendation must be grounded in physical chat models Pi can actually use. A native classifier returns bounded typed answers rather than prose or invented model identifiers. Pi owns classifier discovery, authentication, and transport; users explicitly classify candidate chat models by capability and priority.

Solution

Provide one ordinary Pi tool, preview commands, and an exported core API. Intersect Pi-owned physical chat candidates with exact global configuration and caller restrictions. Ask one explicitly configured native classifier three choice questions and one bool question, validate the answers, and apply deterministic selection policy. Classifier failure returns a typed failure: no fallback of any kind.

Implementation authorized: implement all seven tickets locally. No push, pull request, npm publication, or live model tests.
Responsibility rule: the advisor recommends. It never calls pi.setModel(), never launches agents, and never assumes Paseo or any other orchestrator.

User Stories

  1. As a Pi user, I want a model recommendation for a proposed subtask, so that I can delegate work without changing the parent session model.
  2. As a Paseo user, I want ordinary Pi provider, model, and thinking identifiers, so that Paseo can consume the recommendation without a Paseo-specific adapter.
  3. As a pure-Pi orchestrator author, I want the same recommendation contract, so that I can remain independent of Paseo.
  4. As a user with scoped Pi models, I want that scope treated as a strict allowlist, so that the advisor cannot recommend models I excluded.
  5. As a user without an explicit model scope, I want recommendations limited to Pi models with configured authentication, so that every result is usable.
  6. As a user, I want exact model configuration, so that quality is determined by my judgment rather than price or model-name guesses.
  7. As a user, I want unclassified models excluded automatically, so that newly appearing models do not silently enter routing.
  8. As a user, I want named task profiles to define normal model levels and caller levels to remain hard restrictions, so that routine picking is automatic while stronger exceptions require fresh exact user approval.
  9. As a user, I want image, context, provider, and minimum/maximum-thinking requirements enforced, so that incompatible models are eliminated before selection.
  10. As a user, I want native choice distributions and a bool answer, so that recommendation policy never depends on generated prose.
  11. As a user, I want capability selected from light, standard, advanced, and frontier, so that task demand is separate from model cost.
  12. As a user, I want high-consequence tasks to receive configurable capability floors, so that short security or migration prompts are not underestimated.
  13. As a user, I want config-only task names with optional descriptions, so that my workflow is not constrained by a built-in taxonomy or inferred task labels.
  14. As a user, I want thinking effort selected on Pi's ordered scale, so that reasoning effort is portable across supported providers.
  15. As a user, I want global and per-model thinking clamps, so that cheap models may run at max while other models remain limited to low through medium.
  16. As a caller, I want both minimumThinking and maximumThinking treated as hard bounds, so that an orchestrator's thinking ceiling cannot be exceeded.
  17. As a user, I want unsupported thinking levels resolved through Pi's model metadata, so that provider-specific capability tables are not duplicated.
  18. As a user, I want price considered only after capability and preference, so that price does not masquerade as quality.
  19. As a user, I want the larger context window preferred for semantically context-heavy work when other policy values tie.
  20. As a user, I want one explicit classifier selected from Pi's authenticated classifier inventory, so that Pi owns provider credentials and request handling.
  21. As a user, I want classifier errors and invalid answers returned as typed failures, so that no hidden secondary model or corrective retry runs.
  22. As a user, I want answer probabilities strictly validated, so that native parsing alone cannot admit malformed decisions.
  23. As a user, I want configuration errors to disable the advisor immediately, so that failures are visible before delegation.
  24. As a user, I want global-only policy initially, so that repositories cannot redirect classifier traffic or change model classifications.
  25. As a user, I want Pi's /reload to apply configuration edits, so that the reload boundary is explicit.
  26. As a user, I want doctor to validate configuration, classifier availability, and optional connectivity without making inference calls by default.
  27. As a user, I want a model inventory command, so that I can see eligible, configured, unavailable, and unclassified Pi models.
  28. As an automation author, I want discriminated result statuses, so that every outcome is exhaustively handled.
  29. As a privacy-conscious user, I want task bodies omitted from persistent logs by default, so that calibration metadata does not retain work content.
  30. As a maintainer, I want injected classifier responses and mocked Pi registries, so that normal tests require no credentials or model calls.
  31. As a pi-subagents caller, I want optional read-only launch-contract verification before requesting approval, so that conflicts are visible without coupling the generic advisor to a launcher.

Native Classifier Questions

Question Primitive Criteria Policy use
required_capability Ordered choice light, standard, advanced, frontier 75th percentile becomes the base required class; percentile is configurable.
reasoning_effort Ordered choice off, minimal, low, medium, high, xhigh, max, each with a short task-demand rubric Requested Pi thinking level before clamps and support resolution.
context_demand Ordered choice Ordered semantic context demand from narrow to exceptionally broad Softly prefers a larger context window among otherwise equal models.
high_consequence bool Whether an incorrect result could cause material security, data, release, migration, or operational harm Probability at least 0.70 and below 0.90 floors capability at advanced; 0.90 or above floors at frontier. Thresholds are configurable.

Submit all four questions in one native classification call against explicit task state: task, caller-selected task profile and its optional configured description, role, caller context, and requirements. Profile descriptions are data, not permission to override bounds. Task names are never inferred; unknown explicit names fail input validation. Execution order belongs to Pi and its provider; llama.cpp evaluates questions sequentially. The extension never reads the parent transcript.

Compute the capability percentile from returned probabilities in the configured label order, not from native score expectations, confidence, or rounding. Effort and context use their validated native choice labels. Choice-based thresholds require calibration; wire compatibility alone does not make different classifiers interchangeable.

Implementation Decisions

Package and dependencies

  • Name the product Pi Model Advisor, package it as @schultzp2020/pi-model-advisor, and follow the monorepo's ESM, Rolldown, TypeScript, Vitest, oxfmt, oxlint, and changeset conventions.
  • Target Pi 1.0.4 for the new package. Native classifiers first appeared in Pi 0.99.0. Leave Pi Cursor's dependency unchanged unless workspace compatibility requires a change.
  • Use Pi's classifier registry, request-time authentication, transport retries, and timeout options. Add no custom provider transport or authentication layer.
  • Use Pi's TypeBox schemas for tool input, output, and strict configuration validation. Retain explicit semantic checks for classifier answers.
  • Keep the optional pi-subagents export isolated from default extension/core imports. Use published pi-subagents 0.76.1 as a development dependency for public-contract compatibility tests, not a default runtime dependency.

Candidate ownership

  • Use Pi's scoped models when that collection is nonempty. Otherwise use Pi's authenticated available-model snapshot.
  • Never fetch or maintain an independent candidate catalogue. Exact user configuration classifies the Pi models that may be selected.
  • Configured tasks contains arbitrary named profiles with normal level arrays or { description?, levels } objects. Caller taskKind must match a configured name; omitted means no profile. Request levels remains a hard restriction. Empty task/request arrays block recommendations including escalation. Callers no longer supply candidate model IDs.
  • Models absent from capability groups are unclassified and cannot be automatically recommended. Exclude virtual entries (api === "pi-virtual"); never expand scope to their physical targets.
  • Discover the configured classifier separately with getAvailableOfType("classifier"). Classifiers are not candidate chat models; never select one by guessing from a model name.

Selection order

  1. Validate configuration and discover Pi-owned candidates.
  2. Intersect configured membership, Pi scope, and hard caller levels. Validate any selected profile and reject unknown names. Empty task/request level arrays block the request.
  3. Apply hard image, context, provider, and thinking requirements.
  4. Evaluate and strictly validate three native choice answers and one bool answer. Failure returns the typed result without further inference or stronger-model proposals.
  5. Select required capability from the configurable ordered-choice percentile (default 75), then apply consequence floors (advanced at 0.70; frontier at 0.90). There are no task-kind floors or inferred task names.
  6. Prefer the lowest sufficient compatible capability in the selected profile's normal levels and hard caller levels.
  7. If no normal candidate suffices, consider only sufficient compatible classes above the profile's highest normal level, still inside every hard constraint. Rank one proposal and return approval_required; never proceed without fresh approval of exact provider/model/thinking. Without a selected profile, all hard-allowed classes are normal and no above-profile escalation applies.
  8. If neither pool has a sufficient compatible model, return no_eligible_model. Never relax capability floors, scope, or caller/configured bounds.
  9. Apply user priority across remaining models.
  10. Use context-window size as a soft preference when context demand is high.
  11. Use output price, input price, then cache-read price as late tie-breakers.
  12. Use provider/model identity as the final deterministic tie-breaker.

Thinking policy

  • Map the validated reasoning-effort choice to Pi's ordered levels: off, minimal, low, medium, high, xhigh, max.
  • Intersect global and per-model configured ranges with caller minimumThinking and maximumThinking. An inverted caller range is an invalid request; a model with no supported level inside the intersection is ineligible.
  • Use getSupportedThinkingLevels() and clampThinkingLevel(). Native clamping prefers the next supported higher level, then lower; it is not nearest-level/higher-on-tie.
  • Clamp the request into the permitted interval before native support resolution. If native resolution exceeds the ceiling, use the highest Pi-supported level inside the interval; if it falls below the floor, use the lowest supported level inside. Reject only when that supported intersection is empty. Neither caller bounds nor configured maximums may be relaxed.
  • A configured range containing no Pi-supported level is a configuration error. Caller restrictions that eliminate every candidate return no_eligible_model.
  • The user's Luna configuration pins minimum = maximum = max for both work and personal identities. A caller ceiling below max excludes Luna; never lower its effort. This is exact per-model configuration, not a model-name rule. Max thinking does not raise a model's capability class.

Configuration

  • Load global-only advisor configuration beneath getAgentDir(), respecting PI_CODING_AGENT_DIR. Initial release reads no project overlay.
  • Keep object-style classifier identity: { provider, model }. Group chat-model arrays under models.light, models.standard, models.advanced, and models.frontier. Each entry contains exact provider/model fields and optional priority/thinking overrides; capability belongs to the group.
  • Model presence permits selection; removal excludes it. There are no enabled or local configuration fields. Reject duplicate model identities within or across capability groups. Unused groups and default settings may be omitted.
  • Optional tasks has no reserved keys. Values are level arrays or objects with required levels and optional description. Starter profiles: plan (advanced/frontier), implement (light), review (advanced/frontier), research (standard/advanced), pull_request (standard/advanced). Explicit unknown names are input errors. Empty arrays block the task; array order does not set priority. No inheritance or automatic name inference.
  • Require one exact available classifier identity, hosted or local. Pi's native llama.cpp provider can serve a local classifier such as Clef; use its exact classifier inventory ID. Pi owns server configuration, optional authentication, discovery, and transport. Missing, invalid, or unavailable classifier selection disables recommendation with configuration_error; a local failure never falls back to a hosted classifier.
  • OpenAPI contract records the approved configuration shape, defaults, and result examples.
  • Use strict TypeBox validation; reject unknown keys and invalid policy ranges. Credentials, endpoints, and classifier provider registration belong to Pi, not advisor configuration.
  • Load and validate configuration at extension initialization and Pi's /reload boundary. File edits alone leave the current snapshot unchanged; there is no modification-time watcher or per-invocation file reload.
  • After a reload, malformed configuration disables the advisor instead of restoring an old snapshot. Diagnostics report exact issue paths and the explicit reload boundary.

Classifier validation and failure handling

  • Call ctx.modelRegistry.classify(model, context, options) once. Pi resolves authentication at request time; inspect stopReason and errorMessage, because native calls report errors rather than rejecting.
  • Retain Pi's native transport retries and timeout options. Add no corrective semantic retry, custom retry loop, secondary classifier, chat emulation, or alternate recommendation after failure.
  • Propagate the tool's abort signal or optional ctx.signal, and enforce a configurable overall deadline covering native attempts (default 60 seconds). Cancellation returns aborted; deadline exhaustion returns a typed classifier failure.
  • Require exactly the four expected answers with matching question/type identities. Reject unexpected keys or labels, missing/duplicate probability entries, nonfinite or out-of-range probabilities/confidences, and choice totals with absolute error above 0.0001. Normalize accepted rounding drift before the capability percentile; native parsing alone is insufficient.
  • Distinguish transport, deadline, and invalid-answer failure categories. Preserve reported usage even when answer validation fails; never fabricate a success or replacement model.

Public surfaces

  • Register one ordinary recommend_subagent_model tool, usable directly and through Pi's native codemode. No separate codemode adapter or MCP export server.
  • Supply native TypeBox outputSchema and matching structuredContent; details alone are not the programmatic result. Return nested classifier usage for native session accounting, including failure paths.
  • Declare read-only, nondestructive annotations. Mark classification open-world when task data may leave the machine.
  • Register bare status, recommend, models, config, and doctor forms beneath the /model-advisor command.
  • Export the injectable recommendation core for reuse by other Pi extensions.
  • Use discriminated unions for recommendation status, classifier failure category, and native choice/bool answer type. Pi owns authentication; no advisor authentication-mode union is needed.
  • Return structured data and mechanically derived policy details. Do not generate a prose rationale. recommended describes a normal-pool selection, not universal launch permission. approval_required always blocks proceeding until fresh exact user approval; no advisor result changes approval state.

Optional pi-subagents handoff

  • Expose one helper, verifySubagentRecommendation(), from @schultzp2020/pi-model-advisor/pi-subagents. Keep it outside generic core and default extension imports; no separate package.
  • The caller supplies the recommendation, actual intended launch inputs, current host snapshots, and the official resolveSubagentLaunchContract() function from pi-subagents/preflight. Inject the function; independently installed Pi packages are not necessarily resolvable Node dependencies.
  • Use the public preflight contract only. Supply current parentModel, scopedModelIds, and any host facts required by the intended launch, including runtimeSnapshotHost for native MCP resolution. Missing host facts (host_required) are verification failure, not proof of eligibility.
  • Return the exact verified provider/model/thinking selection or a structured verification failure. A rejection, unresolved contract, or changed model/effort is a conflict: never substitute or silently approve adjusted values.
  • Flow: recommend → verify → user approval of exact selection → caller's existing launcher. Verification is neither approval nor reservation; launch performs authoritative policy checks again.
  • For native Pi children, dispatch model: "provider/id:thinking"; the subagent tool's top-level thinking field does not select child effort. Preserve work/personal provider identities exactly.
  • Resolve and approve every workflow selection before dispatch, then pass exact values into child steps. The workflow sandbox has no classifier API; subagent itself is model-only, not a codemode tool.
  • pi-subagents owns role/provider defaults, scopes, thinking ceilings, and lifecycle. Task profiles define the routine worker pool; the user's implementation profile uses light Luna at max. A stronger compatible exception is only a proposal and requires fresh exact approval. Caller level restrictions remain hard. Adding another light model expands the routine pool. A role default alone cannot prevent an explicit override. Initial helper supports native Pi children, not external CLI translation.

Privacy boundary

Remote classification sends explicit task state through Pi's provider; Pi may retain tool arguments in session transcripts independently of task-free advisor logs. Provider names alone establish neither locality nor retention guarantees. Task state is untrusted data, not an injection guarantee.

Contracts

Tool request

{
  task: string,
  taskKind?: string, // exact configured task profile name
  role?: string,
  context?: string,
  requirements?: {
    imageInput?: boolean,
    minimumContextWindow?: number,
    allowedProviders?: string[],
    minimumThinking?: ThinkingLevel,
    maximumThinking?: ThinkingLevel
  },
  levels?: Capability[]
}

Result discriminators

RecommendationResult is discriminated by status: recommended, approval_required, configuration_error, no_eligible_model, classifier_failed, or aborted. Invalid tool requests are rejected by Pi's input schema; core callers receive equivalent validation errors. Successful results identify the configured classifier and exact selected chat model/thinking, include validated native choice/bool answers and mechanical policy details, and account for reported usage. There is no classifier fallback or automatic stronger-worker substitution. approval_required carries one exact stronger selection pending fresh user approval; scope and hard requirements still apply.

The optional verification helper returns verified or verification_failed separately from RecommendationResult. Verification failures include preflight rejection, missing host facts, and selection conflicts; they do not trigger reclassification or launch.

Testing Decisions

Primary test seam: the exported recommendation operation accepts injected native-classifier execution and a Pi-derived candidate snapshot, then returns a complete discriminated result. Test validation, eligibility, deterministic policy, failure handling, and thinking resolution without a live service or ExtensionContext.
  • Test external recommendation behavior rather than private helper structure.
  • Inject native classifier responses and mock Pi registries, authentication availability, timers, and abort signals.
  • Cover scoped precedence, physical-only filtering, unclassified exclusion, normal-pool/hard-level intersections, custom profile names and descriptions, unknown-name rejection, omitted versus empty rules, stronger proposals with mandatory approval, both thinking bounds, capability choice quantiles, consequence floors, ranking, native support resolution, invalid distributions, native error/abort results, deadlines, reported usage, global-only configuration, /reload, and every result discriminator.
  • Test the optional helper with injected preflight outcomes and the published public contract: exact unchanged selection, rejection, missing host snapshots, thinking adjustment, and stale-snapshot recheck semantics. Assert no launch, fallback, settings mutation, or default-export dependency.
  • Test tool and command registration with the same lightweight Pi API mocking style already used by Pi Cursor.
  • Do not add live classifier or worker calls. CI requires no credentials, local model server, network access, or paid inference.

Out of Scope

  • Switching the parent Pi model or thinking level.
  • Launching, supervising, or terminating subagents.
  • Paseo-specific profiles or APIs.
  • Automatic classification of every parent prompt.
  • Automatic quality inference from price, family names, benchmarks, or model identifiers.
  • An independent model catalogue or models.dev dependency.
  • Learning, adaptive thresholds, or persistent task text by default.
  • Live model integration tests.
  • Project policy overlays, automatic file watching, custom classifier transport/auth, and fallback machinery.
  • Automatic virtual-model routing, launch interception, watchdog integration, profile generation, or an external CLI model adapter.
  • Updating Pi Cursor's Pi dependencies unless compatibility forces it.
  • Publishing the npm package in this work.

Further Notes

  • The user authorized implementation and removed worker-locality requirements. Publication and live model tests remain out of scope.
  • The native-first baseline is Pi 1.0.4 and the optional public preflight compatibility baseline is pi-subagents 0.76.1.
  • Native reference contracts: Pi classifiers, classification answers, and public launch preflight.
  • The design draws most directly from pi-jev-model-router's nonmutating route tool, pi-model-auto's reusable core boundary, and pi-auto-model's ranked structured results, while rejecting parent-model switching and embedded orchestration.
